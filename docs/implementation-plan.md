# HL7 v2 implementation plan

Status: implementation in progress, 2026-11-10. The user has authorized implementation in this repository. Changes in neighboring repositories still require a separate request. See [architecture](architecture.md) for component boundaries, source evidence, accepted decisions and unresolved questions.

Build the smallest complete supported interface before broadening the catalog or mapping families. Every stage ends in observable behavior and failure tests. Do not label a stage complete on the basis of module skeletons, type definitions or happy-path fixtures alone.

## Current progress

| Stage | Status and evidence |
|---|---|
| 0 — Interface contract | Schema source/provenance, representative sender contract and application/durability decisions remain open. Independent wire implementation proceeds as allowed below. |
| 1 — Wire core | Initial parser with a flat arena index, source spans, four-state presence, explicit escape decoding and sparse byte-range editing implemented. No third-party dependencies. Synthetic binary-safe corpus, inspector, deterministic robustness checks and a local timing benchmark are present. Typed NM/DT/DTM/TS interpretation and construction of missing positions are deferred. See [actual supported subset](wire.md). |
| 1 — Remaining verification | Coverage-guided fuzzing, broader sender corpus, allocation/peak-memory benchmarks and expansion beyond the documented delimiter/encoding subset are not complete. Stage 1 is not declared fully closed. |
| 3 — Framing core | Bounded incremental MLLP decoder, buffer/writer encoding, explicit consumed-byte backpressure boundary, poison/reset and EOF handling implemented without dependencies. See [framing contract](mllp.md). |
| 2 and remainder of 3–8 | Not implemented. No schema, async socket transport, ACK, FML map or durable-processing capability is advertised. |

Six core integration tests cover source ownership/round trips, wire presence and positions, escapes, input/resource failures, editing and generated inputs. They include 10,000 generated byte inputs and 2,000 scalar-edit round trips with shuffled delimiters. The README example is compiled and run as a doctest. CI checks formatting, tests and Clippy on the minimum and stable toolchains; local success does not establish a remote CI result.

Three additional framing scenarios cover exhaustive two-part splits, one-byte/coalesced input, EOF at every byte, size/format errors, poison/reset and short/failed writes. The MLLP documentation example is also compiled and run as a doctest. These checks do not yet establish async transport or durable receipt behavior.

## Baseline and decision gates

The inspected repository starts at `cbad76d225214e98129d548fba4170a2c96c605d`, without Cargo or Rust code. The first implementation should use one package with a library, optional features and an optional binary. Implement the HL7 stack as original OctoFHIR code under MIT OR Apache-2.0: no dependency on, vendoring of, or code/test/catalog copying from hl7-rust, er7, EffortlessMetrics/hl7v2-rs or another HL7 implementation. General-purpose infrastructure and the existing OctoFHIR FML/FHIR libraries remain separately selected dependencies. No new mapping language, separate queue service or speculative microcrates is planned.

The following distinctions must survive implementation:

- Accepted direction: original HL7 implementation, independent wire core, schema views, MLLP, explicit ACK boundaries, durable receipt, FML/ConceptMap, separate clinical application and reproducible replay.
- Proposed starting choices: v2.5.1, ADT A01, R4 4.0.1, PostgreSQL, enhanced accept-only acknowledgement and one in-flight outbound message per connection.
- Release blockers: evidenced schema provenance/coverage, representative interface contract, correct presence/precision behavior through FML, and a demonstrated durable clinical receipt boundary.

Stages 1 and transport-codec work in stage 3 can proceed independently of schema distribution. Production schema selection blocks stage 2's release gate and clinical interoperability claims. A direct FML node adapter is an optional upstream workstream; the explicit JSON baseline can complete the first scenario if its semantics pass. Tests must state which adapter they exercise.

## Stage 0 — Freeze the first interface contract

Produce a version-controlled support profile before writing broad APIs. Choose one sender scope and v2.5.1 ADT A01; list required segments/fields, accepted encoding and terminators, permitted Z-segments, identity authorities, processing IDs, payload bounds and ACK behavior. Use synthetic identities only until a de-identified corpus is approved for repository inclusion.

Resolve these technical gates:

1. Establish the source evidence for our own v2.5.1 definitions: obtain the corresponding standard and evaluate the exact candidate official schema archive, recording artifact hashes, terms and provenance. Author the narrow definitions against checked references or generate them using our own importer. Enumerate gaps rather than treating XSD validation as ER7 conformance. If generated data cannot be distributed, define a user-supplied local import workflow. Do not copy another implementation's tables or relabel the Redox/atomic flat catalog as release-specific.
2. Define a minimal schema support matrix for MSH, EVN, PID, PV1, ACK/MSA/ERR and their transitive datatypes, plus the ADT A01 event/structure association. Keep unmapped but structurally allowed content in the source and report it.
3. Select the dependency versions actually to be used. Adjacent FML source declares 0.2.5; both consumers resolve registry FML 0.2.6. The inspected engine boundaries match; their FHIRPath versions differ. Record package/revision selections and the compatible Rust toolchain, then compile a compatibility probe.
4. Select custody and clinical completion boundaries, PostgreSQL durability settings, identity/ownership rules and required R4 validation. Define what a missing identifier, unknown required code or unsupported schema will do.
5. Record upstream changes that would require separate work: an FML tree-ingestion/expression adapter and an atomic server application-receipt capability. Do not edit fml-rs or server-rs as an incidental dependency fix.

**Exit evidence:** one reviewed interface profile, source/provenance manifest, supported-element matrix, synthetic acceptance/rejection fixtures and an ACK contract. Any schema evidence still missing is an explicit blocked release gate, while independent parser work may continue.

## Stage 1 — Implement the lossless wire core

After implementation is requested, create the minimal Cargo package and our own `wire` module. Establish shared byte ownership, positional indexes and source coordinates before adding typed convenience accessors. Derive behavior from the interface contract and checked standards references; do not adapt another parser's implementation.

Deliver generic ER7 parsing, delimiter discovery, raw/token access, four-state presence and original-byte emission. Add an editor with explicit unset/empty/null/value operations and escaping for changed fields. Keep typed decimal/date parsing separate from lexical storage. Bound all structural expansion and avoid schema/FHIR/Tokio dependencies in the core build.

**Exit checks:**

- Byte-for-byte original emission for all accepted fixtures, including custom delimiters, empty tails, repetitions, unknown and Z-segments, non-UTF-8 bytes and preserved unsupported escapes.
- Golden positions and source spans for MSH-1/MSH-2, each hierarchy level, repeated segments, empty slots and explicit nulls.
- Semantic edit/parse round trips for special characters; one-pass escape decoding, malformed escapes and hex-encoded separators/CR cannot change the parsed structure.
- Exact lexical preservation for long decimals, leading zeros, fractional timestamps, partial dates and missing offsets. Invalid typed forms remain inspectable with diagnostics.
- Property/fuzz runs establish no panics, invalid slices or unbounded index growth under declared input limits. Failures become retained regression fixtures.

**Reviewable artifact:** a small parser/inspect/round-trip command or library example, corpus manifest, diagnostics snapshots and parser benchmark baseline. No FHIR conversion claim yet.

## Stage 2 — Import and apply one versioned schema profile

Implement the schema representation, deterministic offline importer, package manifest, exact release resolution and overlay compiler. Keep schema data optional and separately attributable. Load the first approved v2.5.1 subset and explicitly identify structural versus conditional/terminology validation coverage.

Implement grouping as references to wire segment occurrences, not a new owning message tree. Add views and validation for the initial A01 profile, then schema-only fixtures for nested/repeating ORU groups. Add dynamic OBX-5 selection even before an ORU FHIR map, so the model cannot accidentally hard-code OBX-5 as text.

**Exit checks:**

- Re-importing the same artifact with the same importer produces identical output and digest; all references and occurrence constraints are checked.
- Unsupported MSH-12 fails schema resolution while preserving generic parsing. MSH-9.3 takes precedence when valid; conflicting or unknown explicit structures fail. Event fallback is tested only when 9.3 is absent.
- Verify ADT A08's shared-structure association for the selected release as a regression against string concatenation, without claiming an A08 map exists yet.
- Repeated groups, optional branches, repeated segment names, unexpected Z-segments and ambiguous associations have stable occurrence references and explicit diagnostics.
- OBX-2 selects each supported OBX-5 datatype within its own segment; unknown/missing types and invalid/null/empty values remain distinct.
- An overlay cannot silently inherit array tails, change its base package, break references or introduce unbounded ambiguity. Existing receipts continue to resolve their original effective schema after activation of a new revision.

**Release gate:** documented schema provenance, rights/notice handling, version evidence and review of the supported subset. Our synthetic definitions can exercise importer development but cannot pass this conformance gate. Third-party implementation catalogs are not an import source.

## Stage 3 — Implement MLLP, ACK and durable acceptance

Build an incremental framing codec and async receiver/sender with persistent sessions. Separate framing errors from recoverable envelope errors. Start with bounded sequential request/response on each outbound connection; receiving several messages on a persistent connection remains mandatory.

Add version-aware ACK generation/parsing and a policy engine for original/enhanced mode. Implement the `AL/NE/ER/SU` decision matrix, even when the first deployment permits only enhanced `AL/NE` and original completion mode. Unsupported application-ACK routing is rejected during interface activation.

Implement the proposed PostgreSQL receipt store with original bytes, unique scoped message keys, payload digests, attempts, pinned plan references and durable ACK records. Claim ready work from durable rows rather than requiring a second message broker. Return `CA` only after an admissible envelope and an atomic durable receipt. In-memory stores are explicitly ephemeral.

**Exit checks:**

- Every two-part split of representative frames, randomized multi-part splits, one-byte reads, many frames in one read, split trailers and EOF mid-frame behave correctly.
- Oversize/malformed frames, junk, nested start markers and assembly/idle/write timeouts have bounded memory and deterministic close/reject behavior.
- ACK fields, ERR location/escaping, fresh response MSH-10 and exact MSA-2 correlation match fixtures. Wrong, late, duplicate and unrelated ACKs cannot complete another send.
- Acceptance success never precedes the committed receipt/ACK record. Inject commit failure, disk/database refusal, ACK write failure and disconnect after commit.
- Concurrent same-key/same-bytes deliveries share one work item and outcome; changed bytes create a retained conflict and never inherit the original success response.
- Bounded connections, read buffers, durable admission waits, worker queues and ACK output remain bounded under a deliberately stalled consumer.
- Shutdown drains within a deadline, retains committed work and does not acknowledge incomplete frames. Restart can resend a recorded commit ACK without a new application attempt.

**Reviewable artifact:** send/receive/inspect commands against a persistent loopback connection, a restartable durable inbox demo, ACK matrix results and memory/latency measurements. This stage demonstrates durable HL7 custody, not successful FHIR processing.

## Stage 4 — Connect logical models and FML

Generate the logical-model subset from the effective schema and implement stable source-reference mapping. Preserve presence states, repetition positions, numeric lexemes, temporal precision and OBX typing in the logical view.

First establish the compatible path using `fml_model::compile`, `fml_check::check`, R4/HL7 definitions, strict map/ConceptMap resolution and `Engine::transform`. Build at most one source `Value` projection in hl7v2 and pass it directly; do not add a text JSON serialization/deserialization cycle. Cache immutable definitions, compiled maps and expressions across attempts.

Prepare a separate upstream design/probe for direct tree ingestion. Its acceptance comparison must include expression and trace allocations, not just the public `transform` argument. Evaluate the existing shared FHIRPath `FhirNode` and node entry points for expression interoperability, including explicit logical-fragment typing and exact decimal output across `to_json()` boundaries. A lazy node provider is a later option if the simpler direct-loader extension cannot meet measured needs. No private-tree dependency, local FML fork or second evaluator is acceptable.

Author a narrow A01 FML map to R4 Patient and Encounter proposed data. Map explicitly supported identifiers, patient names/demographics, encounter subject/class/status and event evidence; keep their exact support matrix with fixtures. Use ConceptMap for contracted vocabulary, with required unknown translations blocking application. Attach published IG references and local deviations to assets.

**Exit checks:**

- Compile/check both positive maps and maps containing invalid field/type paths. Prove logical-type navigation and filters through the actual selected expression provider, including a dynamic logical datatype probe.
- The four presence states survive projection and map conditions. A null never becomes an unnoticed missing value, and empty components do not shift indexes.
- Exact numeric/temporal probes pass through engine/FHIRPath/output or fail explicitly. Do not accept an `f64` round trip or invented date/time precision.
- Repeated groups and source diagnostics keep their wire associations. Report populated unsupported fields, unmapped codes, deliberate omissions and truncated reports.
- Exact `url|version` requests cannot fall back to another map, ConceptMap or model. Replay refuses missing historical artifacts.
- Source JSON baseline and any direct-ingestion candidate produce equivalent targets, intentions and diagnostics. Allocation/peak-memory reports identify remaining copies, including expressions and tracing.
- Cancellation, execution limits and a bounded worker executor stop runaway maps without retaining unlimited blocking work. Verify the non-`Send` execution strategy against the chosen FML release.

**Reviewable artifact:** offline A01-to-R4 conversion with pinned assets and a machine-readable loss report; no database mutation. Record the chosen source adapter and unresolved upstream API work.

## Stage 5 — Finish the first vertical scenario

Connect durable A01 receipt to conversion, clinical identity resolution, ownership policy, R4 validation and a transactional application sink. A test sink must provide real atomic receipts and idempotency semantics; a mock that returns success without commit behavior cannot close this stage.

Implement one owned-field policy and scoped patient/encounter identity strategy. Validate every converted resource and final merged resource against R4 4.0.1 base definitions including invariants, regardless of `meta.profile`. Validate required profiles and Bundle/reference rules explicitly. Preserve unrelated existing fields, and quarantine ambiguous identity or unsupported event changes.

### First completed scenario

1. A sender keeps one TCP connection open and sends several v2.5.1 A01 frames, including fragmented/coalesced reads, with `MSH-15=AL` and `MSH-16=NE`.
2. The receiver persists exact bytes, scoped identity, pinned plan and commit-ACK record atomically, then returns `CA` correlated by MSA-2.
3. A worker obtains a fenced lease, resolves the exact schema/overlay, converts with pinned FML/ConceptMaps and emits a loss report.
4. The application resolves patient and encounter identifiers, builds allowed changes and validates final R4 resources, including an invariant check with no declared profile.
5. Commit resources and the application receipt atomically, including the required application-ACK decision/bytes or deterministic reconstruction data. Reconcile inbox completion from that receipt if the process restarts before updating inbox state.
6. Resending identical bytes yields the existing outcome and creates no second clinical effect. Reusing the control ID with changed bytes records a conflict and returns the contract's negative response.
7. A required unknown code remains quarantined after `CA`. Installing a sender-specific ConceptMap revision and requesting deliberate reprocessing applies the corrected revision once, preserving history. Historical replay still uses the old revision and old outcome.
8. Run the same supported input under the original clinical-completion contract: no `AA` before clinical commit; mapping/validation failures produce the appropriate application failure. Receipt custody alone cannot pass this variant.

The first deployment may use a local transactional reference sink to prove these boundaries. It is not an OctoFHIR server integration claim until stage 7 passes. A remote FHIR sink cannot pass using a local-only receipt: prove target-side idempotency and unknown-outcome reconciliation or keep it explicitly at custody-only semantics.

### Required crash matrix

| Fault point | Recovery assertion |
|---|---|
| Before/during inbox commit | No success ACK; retry can be admitted normally. |
| After inbox commit, before commit ACK write | Original and work survive; duplicate receives the recorded applicable ACK. |
| After `CA`, before mapping or during conversion | Durable work remains claimable; attempt history explains interruption. |
| During validation or clinical transaction | No partial clinical resources or completion receipt. |
| After clinical commit, before inbox completion | Recovery finds the atomic receipt; no duplicate resource/history/event publication. |
| After original-mode clinical commit, before `AA` write | Resend obtains the recoverable recorded application success without a second write. |
| Worker lease expires and a replacement claims work | Stale worker cannot commit effects, advance state or publish a final ACK. |
| Remote HTTP response is lost, if a remote sink is offered | Query target receipt/reconcile before resending effects; never assume failure means no commit. |

**Exit evidence:** one command-driven end-to-end acceptance run with persisted artifacts, crash/restart evidence, duplicate/conflict assertions, final Patient/Encounter snapshots, full R4 results and latency timestamps. This is the first completed vertical milestone.

## Stage 6 — Add event updates and ORU R01

Expand one event family at a time, with its own support matrix and schema/ConceptMap revisions.

- **A08:** partial patient/encounter updates, null/empty/absent policies, keyed repetition merge and cross-source field ownership. Prove that unchanged data is retained.
- **A03:** discharge transitions, encounter identity, effective times and late-event handling. Test delayed A01/A08 after discharge and explicit reconciliation behavior.
- **ORU R01:** repeated patient/order/observation groups, order/result identity, OBX datatype selection, units/status/code translation, corrections and partial results. Add DiagnosticReport/Observation and other resources only when their lifecycle and identity rules are defined.

**Exit evidence per event:** schema/group fixtures, FML tests, R4 validation including invariants, unknown-code quarantine/reprocessing, duplicate/retry tests and application history demonstrating correct transitions. Never overwrite a final result with a late preliminary result merely because it arrived last.

Add a second HL7 release only after acquiring an independent evidenced package and version-specific fixtures. Produce a schema diff and demonstrate selection/validation differences; do not copy the same catalog under a new release label.

## Stage 7 — Embed in OctoFHIR and support a gateway target

This stage requires a separate explicit request before changing server-rs or other neighboring repositories.

Expose a narrow host integration for initialized FML/terminology services, R4 validation, the normal authorized transaction write path, durable jobs and an atomic HL7 application receipt. Verify actual `pub` versus `pub(crate)` APIs and backend capabilities. Reuse async-job fencing/checkpoint patterns and DICOM source immutability patterns; do not coalesce independent HL7 events as DICOM snapshots.

For the embedded path, resources, history/event publication and the application receipt share the same transaction/fence. For the separate gateway, implement the target's receipt/idempotency protocol and reconciliation; document any weaker guarantee when targeting a generic FHIR server. Share transformation assets and application policy tests across both deployments.

**Exit checks:** the stage 5 crash matrix against real OctoFHIR, authorization and reference validation through the normal write path, no duplicate history/events, shared-service initialization behavior, source-configuration pinning and shutdown/recovery under load. Backend capability refusal must be explicit; a separate database transaction does not pass atomicity.

The existing FHIR benchmark repository can later host comparative end-to-end runs, but its HTTP workloads are not an MLLP benchmark. Any modifications there also require a separate request.

## Stage 8 — Operational completion and performance gates

Provide inspection of originals, attempts, ACK status, loss reports, quarantine reasons and replay lineage. Add dry-run reprocessing/diffs and deliberate apply operations. Keep sensitive payloads out of default logs and metric labels. Enforce retention, access and storage quotas without breaking the negotiated deduplication/replay window.

Complete enhanced application-ACK routing if required by an actual interface, including disconnection recovery and independent response phases. Decide TLS/mTLS termination and principal binding before production exposure; certificate configuration and trust in proxy metadata belong to the deployment/interface contract.

**Exit evidence:** operator exercises for a required unknown code, corrected ConceptMap, failed historical artifact lookup, conflicting payload, storage exhaustion, expired lease, reconnect and bounded shutdown. Publish only measured supported behavior and update README claims accordingly.

## Test corpus

Keep original fixtures as binary-safe files with literal CR bytes, not only escaped strings in source code. Each fixture manifest records origin/license or synthetic generator seed, byte digest, expected generic parse/presence/spans, version/profile, grouping, validation stage/results, map/ConceptMap revisions, target expectations, loss report and expected ACK/processing outcome. Error fixtures need a clear intended fault, while cross-cutting fixtures can combine several valid features.

| Corpus family | Required coverage |
|---|---|
| Wire | Default/custom delimiters, MSH special positions, escaped separators/backslash, double-decoding traps, hex/format/local/charset escapes, malformed escapes, quote/null placement, missing/empty tails, repetitions at every applicable level, whitespace and unknown/Z content. |
| Precision/encoding | Very long and high-scale decimals, invalid NM, partial DT/DTM/TS, fractions/offsets, absent zone, unsupported multibyte encoding, invalid UTF-8, truncation declaration/token and line-ending compatibility. |
| Schema | Exact version, missing/unknown version, explicit structure conflicts, event aliases, nested/repeated/optional groups, repeated segment names with different roles, ambiguous groups, conditional requirements, invalid overlay and OBX-2/5 combinations. |
| MLLP | Fragmentation/coalescence, back-to-back frames, EOF at every marker, invalid trailer, junk/nested starts, oversized and slow frames, persistent reconnects, stalled writes, ACK mismatch/duplicate/late arrival and all acknowledgement conditions. |
| Persistence | Concurrent duplicate/conflict receipts, transaction failure, crash matrix, lease fencing, retry/backoff limits, retention boundaries, fixed-artifact replay and revised reprocessing. |
| FHIR/application | A01/A03/A08/R01 scope fixtures, scoped identities, missing authorities, ambiguous matches, partial updates, explicit clear, ownership conflicts, stale/out-of-order events, result corrections, invariant failure without `meta.profile`, required profile/terminology failures and intra-Bundle references. |

Use three evidence levels: authored synthetic edge cases, licensed public examples, and reviewed de-identified sender samples. Record exact provenance and notices before importing public fixtures. Do not use patient data from neighboring repositories by default. Sanitization must preserve clinically relevant structure and lexical edge cases.

Use property tests for structural invariants, fuzzing for wire/codec/schema bounds, golden fixtures for diagnostics and protocol output, and real transactional fault injection for durability. Author our regression fixtures instead of copying upstream test suites. Optional differential comparisons may invoke a separately installed, pinned independent tool over our fixtures for a mutually supported subset; this does not add its code as a dependency. Any disagreement needs standard/profile adjudication. Another parser's output is not the authority for null or escape behavior.

## Benchmark protocol

Measure progressively from stage 1 onward. Correctness fixtures gate every benchmark run; an implementation that omits required validation or reports losses differently belongs in a different configuration.

| Workload | Included boundary | Primary measurements |
|---|---|---|
| Wire parse/inspect | Payload to positional index, then selected access/decoding | Messages/s, bytes/s, allocations/message, allocated bytes/message, peak memory, malformed-input cost. |
| Serialization | Original emission and edited emission separately | Bytes/s, allocations and content-equivalence checks; original byte passthrough is not edited serialization. |
| Schema | Exact resolution, grouping and stated validation checks | Time/message, allocations, worst supported group depth/repetition and failure cost. |
| Conversion | Source adapter + FML + ConceptMap, with validation timed separately and together | Output parity, wall/CPU time, allocations, peak RSS; JSON baseline versus direct ingestion, trace off/on. |
| Durable receipt | Frame complete to committed original/plan/ACK decision | Acceptance latency, commits/s, database/WAL bytes, contention, queue depth. |
| MLLP custody | Sender frame transmission to correlated accept ACK | Client-observed p50/p95/p99 ACK latency, accepted throughput, connection/reconnect cost and errors. |
| Clinical application | Sender transmission to final FHIR commit/receipt | Separate p50/p95/p99 latency and completion throughput, backlog age, validation and transaction time. |
| Recovery | Restart or lease expiry to recovered completion | Recovery time, duplicate effects/history/events, replay rate and unreconciled outcomes. |

For original clinical-completion ACKs, record application ACK latency separately from enhanced accept ACK latency; they acknowledge different boundaries. For suppressed responses, do not treat a missing latency sample as zero. Instrument server-side frame completion, inbox commit, ACK decision/write, worker claim, conversion, validation and clinical commit, plus client-observed timing; avoid cross-host clock subtraction without synchronization.

Use fixed corpus distributions covering small ADT, larger ORU, many repetitions and near-limit payloads. Vary connection count, in-flight window, worker concurrency, arrival rate and injected downstream delay. Include open-loop offered load to expose backlog and coordinated omission, plus a documented closed-loop connection test. Report offered, accepted, quarantined/rejected and completed rates independently. Count warm-up and drain/backlog consistently; fast receipt followed by ever-growing backlog is not sustainable end-to-end throughput.

Every report records repository/dependency revisions, toolchain/build flags, artifact digests, hardware/OS, corpus hashes, warm/cold cache state, trace/report settings, validation/terminology coverage, ACK contract, database topology, commit/fsync/replication settings, TLS state, connection limits and test duration/repetitions. Publish distributions and run-to-run variation, not just the best throughput. Choose regression thresholds from measured baseline variance; set no unsupported speed target now.

Competitor comparisons require the same messages, validation including R4 invariants, durability/failure model, ACK boundary and clinical write semantics. Parser-only results cannot be compared with a durable gateway as a throughput ranking. Existing FHIR HTTP benchmark results cannot substitute for MLLP or inbox measurements.

## Completion criteria

A stage is complete only when its declared support matrix, positive/negative fixtures, limits and failure evidence are checked in with the implementation. A supported interface needs all stages relevant to its promised ACK and application contract. Broader protocol/version coverage, direct-node FML support, TLS, enhanced application responses and remote exactly-once-like effects remain explicit capabilities with their own gates.

Implementation is authorized. README must distinguish the implemented wire subset from planned schemas, transport, conversion and processing, and must not imply full conformance or production interoperability before their gates pass.
